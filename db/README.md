# CineConecta — Scripts de creación de las bases de datos

```
db/
  README.md               este archivo
  postgres/               montado en el contenedor postgres (docker-entrypoint-initdb.d)
    00_roles.sql          usuarios del motor, extensión btree_gist, esquema cineconecta
    01_schema.sql         tablas, restricciones, índices, trigger y vista
    02_grants.sql         permisos con mínimo privilegio
    03_plans.sql          planes iniciales (valores de ejemplo)
  mongo/init/             montado en el contenedor mongo (docker-entrypoint-initdb.d)
    01_collections.js     colecciones con validador $jsonSchema
    02_indexes.js         índices
    03_users.js           rol y usuarios (solo local)
    04_admin.js           administrador inicial
```

Estos scripts solo crean la estructura, los usuarios y el administrador inicial. Los datos de demostración (cuentas, perfiles, suscripciones, pagos y catálogo) están en `db/demos/` y se cargan aparte; ver el README de la raíz.

---

## 1. Levantar todo en local

Con el `docker-compose.yaml` de la raíz del proyecto:

```bash
docker compose up -d
```

La primera vez, cada contenedor ejecuta sus scripts en orden alfabético. **Los scripts solo corren con los volúmenes vacíos**: después de hacer pull de un cambio en `db/`, reinicialice con `docker compose down -v && docker compose up -d`.

Con los puertos por defecto del compose (si los cambia en `.env`, ajuste la conexión):

| Base | Usuario de la aplicación | Conexión |
|---|---|---|
| PostgreSQL | `cine_app` / `cine_app_dev` | `jdbc:postgresql://localhost:5432/cineconecta` |
| MongoDB | `cineApp` / `cine_app_dev` | `mongodb://cineApp:cine_app_dev@localhost:27017/cineconecta?authSource=cineconecta` |

El usuario `cine` del compose es el administrador del contenedor de PostgreSQL: ejecuta los scripts, pero la aplicación no debe usarlo.

Administrador inicial de la aplicación: `admin@cineconecta.local` / `Admin123*` (solo desarrollo).

**Zona horaria.** El proyecto trabaja en UTC (`TZ` y `PGTZ` en el compose). Las fechas se guardan como `TIMESTAMPTZ` (instantes absolutos) y la aplicación convierte a hora de Colombia al mostrar y al interpretar los filtros de fecha de los informes.

**Autenticación en MongoDB.** Los permisos de `cineApp` y `cineReport` solo se aplican si MongoDB arranca con autenticación, y la imagen oficial la activa únicamente cuando se definen `MONGO_INITDB_ROOT_USERNAME` y `MONGO_INITDB_ROOT_PASSWORD` en el compose. Sin esas variables, los usuarios existen pero cualquiera puede leer y escribir todo.

## 2. En la nube

**PostgreSQL (Neon o Supabase)**
1. Ejecutar los cuatro `.sql` en orden con el usuario dueño del proyecto:
   `psql "<cadena>" -v ON_ERROR_STOP=1 -f db/postgres/00_roles.sql` (y así con los demás).
2. Cambiar las contraseñas de desarrollo: `ALTER ROLE cine_app PASSWORD '...';` (igual para `cine_owner` y `cine_report`).
3. Usar la conexión **directa** (no el *pooler* en modo transacción), porque rompe las sentencias preparadas de JDBC.

**MongoDB Atlas**
1. Ejecutar `01_collections.js`, `02_indexes.js` y `04_admin.js` (en `db/mongo/init/`) con `mongosh "<cadena>" --file ...`, pasando `ADMIN_PASSWORD_HASH` con un hash BCrypt nuevo.
2. **No ejecutar `03_users.js`**: en Atlas los usuarios y roles se crean desde *Database Access*. Replicar los permisos que define ese script.

## 3. Qué cambia respecto al modelo suministrado (y por qué)

| Cambio | Justificación |
|---|---|
| `VARCHAR2` → `VARCHAR`, `NUMBER` → `NUMERIC` | Traducción de tipos de Oracle a PostgreSQL. |
| `TIMESTAMP` → `TIMESTAMPTZ` | Guarda instantes absolutos. El informe de consumo compara fechas de sesiones de MongoDB (UTC) con la vigencia de las suscripciones. |
| IDs `GENERATED BY DEFAULT AS IDENTITY` | Los genera la base, pero el seed puede insertar IDs explícitos si los necesita. |
| `PLANS.isActive` (columna nueva) | Gestión de planes por el administrador: un plan inactivo no se ofrece en nuevas contrataciones. |
| Esquema `cineconecta` | Separa los objetos del proyecto de `public` y permite dar permisos por esquema. |

Las tablas, columnas, relaciones e índices únicos del modelo (`ux_accounts_email_ci`, `ux_profiles_name_ci`, `uq_plans_name`, `uq_payments_subscription`, `uq_payments_reference`) se conservan.

## 4. Reglas del negocio que garantiza cada base

**PostgreSQL**

| Regla | Mecanismo |
|---|---|
| Correo y nombre de perfil únicos, sin distinguir mayúsculas | Índices únicos del modelo |
| Una suscripción dura 30 días | `CHECK (endsAt = startsAt + 720 horas)` |
| Sin períodos superpuestos por cuenta (incluye compras simultáneas) | `EXCLUDE USING gist` con rango `[inicio, fin)`; la segunda compra falla con `23P01` |
| Cada suscripción tiene **exactamente** un pago | `UNIQUE (subscriptionId)` + trigger diferido que, al hacer COMMIT, rechaza una suscripción sin pago |
| Estados `'Y'/'N'`, clasificación 0–18, precio > 0 | `CHECK` |
| Nada se borra; el historial no se modifica | `cine_app` no tiene DELETE en ninguna tabla, y solo INSERT en `subscriptions` y `payments` |
| El precio y el máximo de perfiles de un plan no cambian | `cine_app` solo puede actualizar `name` e `isActive` de `plans` |
| Suscripción vigente | Vista `v_current_subscription` |

**MongoDB**

| Regla | Mecanismo |
|---|---|
| Datos obligatorios de cada tipo de contenido | `$jsonSchema` sobre el modelo del módulo catalog: metadatos comunes en la raíz y datos del tipo en `contentDetails` |
| Una serie publicada tiene al menos una temporada con un episodio | `$jsonSchema` (en borrador puede estar incompleta) |
| Un mismo título no se repite en el mismo año | Índice único `ux_contents_title_year` sobre `titleNormalized` + `year` |
| Estados y tipos válidos; clasificación 0–18 | `enum` y rangos en `$jsonSchema` |
| Sin duplicados en "Mi lista" | `uniqueItems` en `contentIds` (y `$addToSet` al agregar) |
| Las sesiones de series llevan el episodio | `$jsonSchema` (`episodeId` obligatorio si `contentType = SERIES`) |
| El identificador de un episodio no se repite entre series | Índice único parcial sobre `seasons.episodes.episodeId` |
| Correo de administrador único y en minúsculas; contraseña como hash BCrypt | Índice único + `pattern` en `$jsonSchema` |
| La aplicación no crea administradores | `cineApp` solo tiene `find` sobre `admin_users` |

**Lo que queda en la aplicación** (ninguna base puede garantizarlo sola): la verificación V1 entre las dos bases, el filtro por clasificación del perfil, perfiles activos ≤ máximo del plan, el cálculo del tiempo visto y del 90 %, que el tipo de contenido no cambie, y que los números de temporada y episodio no se repitan dentro de una serie.

## 5. Pruebas realizadas

- **PostgreSQL** (en PostgreSQL 16, con el usuario `cine_app`; el proyecto usa la imagen 17, compatible): correo repetido con otras mayúsculas, compra válida, compra superpuesta, suscripción sin pago (falla al COMMIT y no queda nada), duración distinta de 30 días, nombre de perfil repetido, cambio de precio de un plan, DELETE y modificación del historial: todos se comportan como se espera. Dos compras **simultáneas** para la misma cuenta: una se confirma y la otra falla con `23P01`, sin pagos huérfanos.
- **MongoDB**: los scripts se ejecutaron contra un `db` simulado (sintaxis y llamadas), y los validadores se probaron con 19 documentos de ejemplo, válidos e inválidos, todos con el resultado esperado. **Falta ejecutarlos contra un MongoDB real** (`docker compose up -d`), porque en el entorno donde se prepararon no se podía descargar el servidor.

## 6. Notas para quienes implementan

- **JPA y permisos por columna.** Las columnas que `cine_app` no puede actualizar (por ejemplo `plans.price`, `profiles.accountId`) deben llevar `@Column(updatable = false)`, o la entidad `@DynamicUpdate`. Si no, Hibernate intenta actualizarlas y PostgreSQL lo rechaza. Las entidades de `subscriptions` y `payments` deberían ser inmutables (`@Immutable`).
- **Enteros en MongoDB.** Los validadores exigen `int` (32 bits) en IDs de PostgreSQL, duraciones y posiciones. En Java, usar `Integer` (no `Long` ni `Double`). En `mongosh`, usar `NumberInt(...)`.
- **Índices en Spring Data MongoDB.** Dejar `spring.data.mongodb.auto-index-creation=false`: los índices los crea `02_indexes.js`, y `cineApp` no tiene permiso para crearlos.
- **Planes de ejemplo.** `03_plans.sql` trae valores inventados. Si el anexo del enunciado define los planes, reemplazarlos por esos.
- **Identificadores del catálogo.** `contentId` es un `ObjectId` y `episodeId` es un UUID en texto, como los genera el módulo catalog. Si cambia el modelo de `Content`, hay que ajustar el validador de `01_collections.js`.
